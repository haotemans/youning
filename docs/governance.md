# 攸宁开发治理协议

[文档索引](README.md) · [决策台账](decision-log.md)

> 本文件约束文档、架构与代码如何同步演进，防止"文档活成化石"。

## 1. 单一事实源

- GitHub 仓库 `haotemans/youning` 是权威来源；源代码与 `docs/` 同仓演进，git log 记录变更。当前 Cargo 包与运行数据仍沿用 `yuantuan` 兼容名称。
- 以 Git 仓库当前分支及远程提交为准；不把历史开发机的本地路径设为通用开发约束。

## 2. 提交纪律

- **每次更改、每完成一个任务：必须本地 commit + 远程 push，一次一档，不许攒批。**
- 一个任务一个 commit，commit message 格式：`type: subject`
  - type：`docs` / `adr` / `feat` / `fix` / `refactor` / `chore`
  - subject：一句话说清干了什么
- 禁止 force push 到 main；推错就走 revert 新提交。

## 3. 变更分级

- **小改**（字段增删、措辞、参数默认值）：直接改文档 + 修订记录加一行。
- **大改**（难逆转、有真实取舍、推翻已定稿内容）：先写新 ADR（编号递增）。被推翻的旧 ADR 标注 `superseded by ADR-NNNN`，**不删除**——留下当年为什么那样定。
- **每条裁决登记台账**：所有拷问裁决（无论大小）记入 [docs/decision-log.md](decision-log.md)（问题/裁决/被否项/落点）；改判追加新行不删旧行。

## 4. 冲突裁决

代码与文档冲突时，合法出路只有两条：

1. 改代码迁就文档；
2. 走变更流程改文档。

唯一非法状态：代码行为变更而文档不更新。发现旧历史文档与现行代码不同，先核对实际实现和设计意图；历史记录保留，当前功能文档准确标注差异。

## 5. 版本节奏

- V0.1：设计基线版本，不据此推断各功能当前的实施进度。
- V0.x：实现期迭代，每次定稿递增并记修订记录。
- V1.0：MVP 闭环跑通且逐章核对文档与代码一致，封板；其后只走 ADR 增量。

## 6. 文档归属与状态

- [文档索引](README.md)是统一入口：`design/` 维护目标与设计约束，`reference/` 维护实现参考和数据基线，代码是实际行为与迁移的事实来源。
- `changes/` 保存未关闭或尚待核对的工作记录；明确关闭的记录进入 `archive/changes/`，故障复盘进入 `archive/incidents/`，保留验证边界。
- ADR 与决策台账按日期保留；`accepted` 表示决定被接受，不能替代实现验收。旧决定被修订时标明关系，不覆盖历史。
- 文档整理不自动扩大为程序修改。已发现的实现差距继续记入工作记录与实现参考，不能改写目标来掩盖缺陷。
- 移动文件时同步入口、相对链接与代码中的文档路径引用；同一结论只保留一个维护位置，其余链接过去。

## 7. 功能与代码双向映射

- [功能索引](features/README.md)和 [`catalog.json`](features/catalog.json) 记录唯一主功能文档、受监管源码文件、验证入口。按行为聚合成一功能一文档，而非一文件一文档；实现文档从代码核对，不能把设计目标写成已完成。
- 同一功能新增或修改代码、测试、API、界面，需在同一 PR 更新该功能主文档；源码新增/删除/移动须更新映射清单。跨功能逻辑使用链接，避免重复维护。
- CI 运行 `python3 scripts/check_feature_docs.py` 检查源码覆盖、唯一归属、文档与测试路径。结构检查不能判断描述真实性；真实 QQ/外部服务的端到端测试单独记载证据。
- `AGENTS.md` 里的 NapCat 部署边界仍然有效；文档变更不授权重启、重建 NapCat。
